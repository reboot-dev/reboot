# Declared transaction-task outcome contract map

Base: `b8c8ed34f9e0cd75073a75ef8371171bcb48ae8d` (PR216). This checkpoint prioritizes declared errors; pure transaction-only adapter ownership is deferred.

## Source-backed Python and native contracts

- `reboot/templates/reboot.py.j2:861-946`: ordinary generated transaction RPC dispatch under the task workflow, stable `Idempotency(alias=f'Task {UUID}')`; only a proto-declared Aborted becomes a durable error terminal. Unknown errors remain retry failures. Admission is the original application RPC, not Tasks.Spawn.
- `reboot/aio/internals/tasks_dispatcher.py:225-305`: a returned typed error is packed as `google.rpc.Status` and ends the retry loop; exceptions do not become declared terminals.
- `reboot/aio/state_managers.py:4700-4785`: tasks are staged transaction effects; completion is a separate durable operation under actor locking. Python does not turn a failed transaction into a successful ordinary writer.
- `reboot/server/database.cc:3351-3555` ParticipantPrepare/Commit/Abort and the canonical `TransactionParticipantAbortRequest`: legacy 2PC owns actual state/task rollback. Abort itself cannot atomically carry an application error receipt. A response-journal Store after Abort is a distinct operation, not part of a successful transaction commit.

## Chosen implementation and observable conditions

1. The immutable generated canonical transaction declaration carries its explicit error schema. Shared and factory task targets retain their admission fences. Ordinary writers do not acquire transaction-task authority. Existing no-error transaction domains and scheduling receipts remain byte-for-byte unchanged.
2. A generated typed root error is terminal-eligible only for the exact bound automatic root receipt on a registered canonical transaction target. A doomed/uncertain outbound context is not a declared business outcome. Complete membership is sealed before registered Abort; the original root guard consumes Abort ownership.
3. An error receipt is staged on the original pending root incarnation, not in successful PendingActorEffects. The actual legacy coordinator acknowledges child Abort first. The root's actor-only native Abort then acknowledges, and a synchronous error-receipt-only Store follows **while the original participant retains its exclusive actor lease**. Only then can admission release and the generated root return an acknowledged declared status. An extra process-local key mutex would leave an unsafe cross-method/ordinary-writer release gap; it is not the chosen implementation.
4. Native Abort, error-receipt Store, source result-journal Store and terminal CompleteTask CAS remain four separate ACK boundaries. Lost receipt Store ACK retains the participant slot, marks actor commit uncertainty and cannot return a declared terminal. Restart recovers actual native records and retries the original transaction-domain target identity. A crash before error receipt persistence may reexecute an aborted handler; arbitrary external effects are not exactly-once.
5. The target error receipt has a distinct `reboot.transaction.aborted-result.v1` fingerprint domain, exact original request fingerprint and ordered declared error-type URL-list digest. Actor identity, root scope, task-id absence, payload and rich-status decoding are checked before replay. Successful response receipts retain their existing encoding. Source task/workflow scope is separate from target root scope.
6. Recovered execution consults current target authorization before target receipt replay, including a previously acknowledged error. Only a target-acknowledged error followed by source-journal ACK can seal a typed terminal. Transport/authorization/unknown/malformed/uncertain failures remain failed attempts, never catch-and-continue authority. Generated ordinary workflow transaction references keep their previous failure contract; the declared-outcome invocation is canonical-transaction-task only.
7. Canonical error results normalize to Python's ABORTED status while preserving the declared payload/message. Canonical Python FailTask and generated Rust TasksWait::fail must decode the same declared BelowThreshold with required=4242/observed=7. Both mutated root/child states must remain unchanged and the child's successfully staged Query successor must not escape. Retained terminal bytes must survive Database/application restart without handler redispatch.

## Bounded acceptance and unchanged limits

The native fixture uses generated Python WeakReference.spawn(Fail), the generated public transaction adapter, original registered root/child participants and existing C++ Database/RocksDB. No raw state seeding, replacement database, new capacity, installs or deployment are authorized. Native positive/error ACK-loss evidence, precise old-admission/receipt-replay negatives, source/generated/executable binding, original child joins and strict downstream Clippy are acceptance requirements, not implied by this map.

Due/running transaction Cancel remains unsupported; only future cancellation is eligible for synchronous terminal CAS. Shared/factory tasks, pure transaction-only adapters, dynamic placement, remote-child receipt-bound composition, automatic Python retry/private-token and recovered-user-identity parity remain outside this checkpoint. Future successor execution and arbitrary handler external-effect exactly-once behavior are not claimed.
