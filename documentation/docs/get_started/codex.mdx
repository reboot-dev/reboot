# Get Started (with Codex)

Build a full-stack app — a Reboot backend behind a standalone React
frontend served at a normal URL — using
[Codex](https://developers.openai.com/codex/) and the Reboot
plugin. Codex writes the code for you: describe the app, approve
the proposed design, and it scaffolds the Reboot backend, React
frontend, tests, and local development setup.

## Install the Reboot plugin

The plugin bundles everything Reboot needs, so the only prerequisite is
[Codex](https://developers.openai.com/codex/cli) itself (installed and
authenticated).

<Tabs groupId="install-method">
  <TabItem value="quick" label="Quick install">

Install the Reboot plugin for Codex with a single command:

```sh
curl -fsSL https://reboot.dev/install.sh | bash
```

The installer detects Codex, registers the Reboot plugin marketplace,
installs the plugin, enables Codex hooks, and pre-installs the pinned
tool shims used by the skill.

:::warning Temporary Codex sandbox opt-out
The installer currently asks to disable Codex's sandbox globally by
writing `sandbox_mode = "danger-full-access"` into
`~/.codex/config.toml`. This is a temporary workaround for an upstream
Codex issue that breaks Python asyncio cross-thread wakeups inside the
sandbox. Reboot's main commands (`rbt generate`, `rbt dev run`, and
related commands) rely on that asyncio behavior.

If you accept the prompt, the installer tags the setting with a
`# reboot-plugin (managed)` comment so it is easy to find and remove
later. If you decline, the Codex install is skipped because the
plugin's main commands will not work reliably under the current
sandbox behavior.
:::

Restart Codex after installation so the new plugin, skills, hooks, and
PATH configuration are loaded.

  </TabItem>
  <TabItem value="manual" label="Manual install">

Register the Reboot plugin marketplace and install the plugin yourself:

```sh
codex plugin marketplace add reboot-dev/reboot-plugin
```

```sh
codex plugin add reboot@reboot-plugin
```

Then add the required Codex settings to `~/.codex/config.toml`. Codex
prints the plugin install path in `codex plugin list`; use it to build
the PATH entry for your machine:

```sh
REBOOT_PLUGIN_ROOT="$(codex plugin list \
  | awk '$1 == "reboot@reboot-plugin" {print $NF; exit}')"

printf 'features.hooks = true\n'
printf 'shell_environment_policy.set.PATH = "%s/bin:%s"\n' \
  "$REBOOT_PLUGIN_ROOT" "$PATH"
printf 'sandbox_mode = "danger-full-access"\n'
```

Copy the output into `~/.codex/config.toml`, at the **top** of the
file (dotted keys pasted below a `[table]` header would become part of
that table). It should look like this, with your actual plugin path:

```toml
features.hooks = true
shell_environment_policy.set.PATH = "/path/from/codex/plugin/list/bin:/your/existing/path"
sandbox_mode = "danger-full-access"
```

:::warning Merge with your existing config
TOML forbids defining the same key or table twice, and Codex refuses
to start on such a config ("duplicate key"). If your config already
has a `[features]` or `[shell_environment_policy]` table, or already
sets `sandbox_mode`, set the values inside your existing tables
instead of pasting the dotted keys above — e.g. add `hooks = true`
under your `[features]` table.
:::

Restart Codex after changing the config.

  </TabItem>
</Tabs>

## Use the skill

In Codex, you do not need a slash command. Start from a normal prompt:

```
Build a Reboot web app where users can sign up and keep a list of chat rooms
```

Codex selects the Reboot app skill from the prompt and routes to the
Web App builder — "web app" (or "website", "SPA", "in the browser",
or a URL) is what tells it you want a standalone browser frontend
rather than an AI Chat App. If your description doesn't say, it asks
first. The builder settles the design before it writes any code. It
will:

1. Analyze your description and propose a state model.
2. Map out the application types, methods, the pages the frontend
   needs, and how users sign in.
3. State that design back to you — so you can redirect it before
   the code exists.

Codex then scaffolds the full project — API definition, backend
servicers, React SPA, and configuration — builds it, writes and runs
backend tests, and starts the app.

:::info The agent-driven path builds a Python backend
The skill scaffolds a Python backend with a React frontend. If you
want a **TypeScript** backend, follow the hand-written
[TypeScript guide](/get_started/typescript) instead — but note
that TypeScript backend support is in alpha.
:::

## What gets created

The skill generates a complete full-stack Reboot app. The most
relevant files are:

```
my-app/
├── .rbtrc                    # Reboot CLI config
├── pyproject.toml            # Python deps (uv)
├── api/
│   └── my_app/v1/
│       └── my_app.py         # API definition (Pydantic)
├── backend/
│   ├── api/                  # Generated Python bindings
│   ├── src/
│   │   ├── main.py           # Application entrypoint
│   │   └── servicers/
│   │       └── my_app.py     # Servicer implementation
│   └── tests/
│       └── my_app_test.py    # Backend behavior tests
└── frontend/
    ├── package.json
    ├── build.mjs             # Discovers + builds every UI
    ├── vite.config.ts        # Vite dev server + build config
    ├── index.css             # Theme variables
    ├── api/                  # Generated React bindings
    └── web/                  # The standalone browser SPA
        ├── index.html
        ├── .env.development  # VITE_REBOOT_URL=http://localhost:9991
        └── src/
            ├── main.tsx      # RebootClientProvider entry
            └── App.tsx       # Routes + top-level component
```

Each entity your app manages becomes its own
[durable state type](/define/overview) with its own
methods; the frontend calls those methods through the typed
[React hooks](/call/from_react) that `rbt generate`
emits into `frontend/api`. If your app has per-user state, the
skill also declares a `User` type and signs browser users in
through Reboot's [built-in OAuth support](/users/authorization) —
`Development()` in development, so you can sign in as any
identity without registering a provider first.

## Test your app

Codex writes backend unit tests covering your app's user
stories and runs them before handing the app off — they help to
make sure that your app works, and keeps working.

Once the tests pass, Codex starts everything the app needs:

* the Reboot backend (`rbt dev run`), which serves your API at
  `http://localhost:9991`, and
* the Vite dev server, on `http://localhost:4444`.

It then hands you `http://localhost:4444`, which redirects to your
web app. In development, click "Sign in" and pick (or make up) a
`Development` identity; signing in auto-constructs your `User`.

## Iterate on your app

You can use the same skill to modify an existing app:

```
Add a page that shows the messages in a single chat room.
```

Codex reads the current Reboot project, proposes a plan, waits for your
approval, then updates the API, servicers, React pages, and tests.

## Run it again later

If you close Codex and come back to the project later, ask Codex to run
the Reboot app again:

```
Run my Reboot app in ./my-app
```

Or just say "Run this Reboot app" from the project directory. The
run skill starts the backend and the frontend dev server and points
you at the app.
